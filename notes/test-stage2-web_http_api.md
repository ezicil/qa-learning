Теория
Т1. Браузер ---> DNS-сервер (получение  ip по домену) ---> Запрос ---> прокси ---> Сервер ---> Ответ сервера ---> Браузер ---> Отображение страницы

Т2. HTTP-запрос - запрос от клиента к серверу. HTTP-ответ - ответ от сервера клиенту. Основные составляющие: Запрос: метод, заголовки, тело. Ответ: код ответа, заголовки, тело ответа. Пример запроса: GET example.com/login. Пример ответа: 200 OK + запрошенный ресурс в теле ответа.

Т3. Network - вкладка позволяющая наглядно отслеживать запросы клиента и ответы сервера. Application - вкладка позволяющая просматривать ресурсы веб-приложения,  в том числе Cookie и JWT. Там буду искать какие данные сохраняются после авторизации, так как зачастую данные такого плана сохраняются в браузере в виде куки, в то время как на сервере в виде сессии.

Т4. GET - запрос на получение какой-либо информации с сервера (например загрузка страницы сайта). POST - запрос на создание какой либо сущности на сервере (регистрация пользователя). PUT - полное изменение сущности на сервере (замена поста на другой). PATCH - частичное изменение сущности на сервере (смена никнейма пользователя). DELETE - удаление сущности на сервере (удаление аккаунта, поста). 
Идемпотентность метода - это свойство метода. Метод называется идемпотентным если при выполнении одного и того же запроса один или несколько раз, результат не меняется и не изменяет состояние сервера.
Идемпотентные методы: GET, PUT, HEAD, TRACE, OPTIONS, DELETE.
PUT - требует в теле запроса полные параметры изменяемой сущности. PATCH - любое количество существующих.

T5. 200 - запрос обработан, 201 - создана сущность, 204 - нет ответа для запроса, 400 - сервер не может обработать запрос, чаще всего синтаксическая ошибка в запросе, 401 - не авторизованный запрос, 403 - нет прав доступа к результату выполнения запроса, 404 - контент не найден, 409 - запрос конфликтует с состоянием сервера, 422 - запрос сформирован правильно, но невозможно выполнить из-за семантических ошибок, 500 - ошибка сервера, 502 - недопустимый ответ с целевого сервера, 503 - сервер не может обработать запрос в данный момент.

Т6. Cookie - файлы, хранящие некоторые данные сервера на стороне клиента. Session - данные о клиенте, хранящиеся на стороне сервера. Cookie используются для идентификации клиента на сервере и для получения его сессии. К Cookie имеет доступ любой кто имеет доступ к клиенту, то есть к браузеру. К сессии имеет доступ только сервер. 

Т7. JWT - JSON Web Token. Используется для подтверждения подлинности. Состоит из 3 частей: xxx.yyy.zzz. XXX - Заголовок - это часть в которой хранится системная информация (алгоритм шифрования, типа токена и т.п.). YYY - Данные - Информация о текущем пользователе. ZZZ - Сигнатура - сгенерированная закодированная строка, которая определяет подлинность JWT-токена. Состоит из заголовка и данных, закодированных с использованием ключа, который хранится на сервере. По умолчаню данные не являются зашифрованными. Изменить данные просто так нельзя, ибо сигнатура останется со старыми данными, соответственно подлинность токена не будет подтверждена.

Т8. Workspace - рабочее пространство, тут находятся все коллекции, среды и т.п. 
Коллекция - набор запросов к какому либо ресурсу. Среда - набор переменных, который позволяет использовать одни и те же запросы к разным версиям ресурсов (Например dev и prod версии приложения). Переменные - переменные используемые в коллекции.
В случае с несколькими запросами к одному API, следует создать переменную коллекции, например baseUrl, куда запишется URL к API, а в запросах использовать форму {{baseUrl}}/ручка.

Т9. pm.test() используется для организации какого-либо теста в каком-либо запросе в Postman. pm.response - ответ от сервера, pm.response.json() - ответ от сервера в формате JSON. 
Статус ответа 200:

pm.test("Status code is 200", function() {
	pm.response.to.have.status(200);
})

В теле присутсвует поле id:

pm.test("Id is got", function () {
	 pm.expect(pm.response.json()).to.have.property("id");
})

Т10. Для ручки POST /user следует выполнить проверки валидации данных, возможно безопасности базовые, проверки структуры ответных данных, проверки кодов ответов на различные случаи. Все проверки данных и валидации следует сопроводить как негативными, так и позитивными тестами. 
Позитивное тестирование - тестирование того, как должно быть. Например регистрация с валидными данными, удаление поста, будучи авторизованным и имея права на это, вход в аккаунт с верным паролем и именем пользователя. Негативное тестирование - тестирование реакции приложения на ошибочные случаи. Например - регистрация пользователя без имени пользователя, вход в аккаунт с неправильным паролем, запрос требующий токена, без токена.
